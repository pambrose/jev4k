# jev4k API conformance check

Checked 2026-10-15, at commit `6f5eb01` on the `0.2.3-dev` branch, against the live TypeSafe docs at
<https://docs.typesafe.ai/api> and the rest of the site. The cached copy in `jev-docs/` was fetched 2026-09-18/19.
Since then TypeSafe has shipped Jev 1.14 (2026-10-14), Python SDK 0.7.1 to 0.7.5 and JS SDK 0.7.0. The method is
described at the end.

**Verdict:** everything jev4k sends and reads still matches the API, with one exception: the API now has a 64-level
nesting limit, and jev4k's request check allows 128 levels (#1). The API has also gained features jev4k doesn't
model, all of them opt-in and two of them marked experimental (#4–#7). The local docs cache and its refresh script
are out of date (#2, #3).

Every issue has a number. Tick its box when it's fixed, and update the count below in the same change.

**Status: 6 of 9 fixed.** 3 medium, 4 low, 2 nit.

## What still matches

Checked and unchanged, or changed in a way jev4k already handles:

- **Endpoint and request shape.** `POST /v1/systemone` with `state`, `model` and `questions`, and Bearer auth. The
  `state` must still be a string, an object or an array. JS SDK 0.7.0 now also rejects a `null` state, as jev4k
  already did.
- **Structured criteria.** The API reference now types Choice option values as `string | object | array | null`, Score
  levels as `array<string | object | array>`, and Noul `true`/`false` as `string | object | array`. jev4k already
  stores all of them as `JsonElement` (`Questions.kt:52`, `:58`).
- **Question limits.** Choice allows 1..255 options. Score allows up to 10 levels; the page now says a Score "should
  have at least two", and JS SDK 0.7.0 still rejects fewer than two, so jev4k's 2..10 is right. Noul `instructions`
  is still required by the HTTP reference. JS SDK 0.7.0 now accepts a Noul with only `criteria`, but the API
  reference doesn't document that.
- **Numbers.** The API rejects NaN, infinities and numbers such as `1e400`. `hasNonFiniteNumber` rejects all three
  before sending, since `1e400` parses to infinity.
- **Answers.** The Noul, Choice and Score answer shapes are unchanged. `usage` token counts may now be `null` (JS SDK
  0.7.0), and `Usage` already has nullable fields. The examples now return Choice probabilities out of declaration
  order, and `ResponseMapper` already reorders them. A new answer type (`box`) becomes `UnknownAnswer`, as the
  `Answer` KDoc promises.
- **Errors.** The table adds `400` (request-rule violations, `max_tokens_exceeded`, images not enabled), `413` (over
  32 MiB) and `415` (bad `Content-Encoding`). `400` maps to `JevBadRequestException`. `413` and `415` fall through to
  the base `JevApiException` and aren't retried, matching both SDKs, which have no dedicated class for either.
- **Retries, timeouts and exception classes.** The SDK retry, exception and constants pages and JS `RetryPolicy` are
  unchanged once Mintlify's added footer is ignored.
- **Models.** `GET /v1/models` still returns `name`, `description` and `release_date`. `jev-latest` still points at
  `jev-1.13.0`, which jev4k's default model and test fixtures use. `jev-preview` now points at `jev-1.14.0`.
- **Encoding.** UTF-8 JSON without a BOM, which `TextContent` produces.

## Issues

### Medium

<a id="issue-1"></a>

#### 1. Validation: the request nesting limit is 128, the API's is 64

The API reference's new "Request rules" section says: "At most 64 nested levels of objects and arrays in each of
`state`, `instructions`, and `criteria`." A request that breaks the rule gets a `400`. jev4k checks every value it
sends against `MAX_JSON_DEPTH = 128` (`internal/JsonDepth.kt:16`), a limit chosen to keep kotlinx.serialization from
overflowing the stack. So a state or question entry nested 65 to 128 levels passes `validate`, goes over the
network, and fails with `JevBadRequestException` instead of `JevValidationException`. That breaks the rule that
every problem is collected before anything is sent. `ClientTest` currently sends a 128-level state and expects it to
succeed (`ClientTest.kt:566`).

Fix: add a sending limit of 64 to `sendProblem` and keep 128 for parsing responses, where the limit only protects
the stack. Choice and Noul criteria are maps whose values jev4k checks one at a time. If the API counts the map
itself as a level, each value can nest only 63 deep, so probe that first (step 2 of the plan). Update
`ValidationTest`, `ClientTest`, `CallOptionsTest`, the CLAUDE.md paragraph on `MAX_JSON_DEPTH`, and the changelog.

**Fixed.** A probe settled the counting. The API rejects a `state` or `instructions` value at 65 levels and accepts
64, counting the outermost container as level 1, as jev4k does. It checks each criteria value on its own: a Choice
option, a Noul `true` or a Score level nested 64 deep inside its map or array is accepted, and 65 deep is rejected.
Every 400 says "Request JSON nesting exceeds the maximum depth of 64." `MAX_SEND_DEPTH = 64` now limits every value
jev4k sends: the state, each question entry, and each `extraBody` field, which the API doesn't cover but which keeps
one rule for everything sent. `MAX_JSON_DEPTH = 128` still limits responses. The tests pin 64 and cover each kind of
criteria value, both at the limit and one level past it.

<a id="issue-2"></a>

#### 2. Tooling: `make api-docs` fails on a removed page

`jev-docs/refresh.sh` downloads every page in `llms.txt`, plus `EXTRA_PAGES=(migrating-to-v1.md)`. That page now
returns 404 (`https://docs.typesafe.ai/migrating-to-v1` does too), and the script exits with "1 page(s) failed;
leaving pages untouched". Nobody can refresh the cache until this is fixed.

Fix: delete `EXTRA_PAGES` and its `printf` line. Emptying the array isn't enough: under `set -u`, macOS's bash 3.2
fails on `"${EXTRA_PAGES[@]}"` with "unbound variable", which I hit while checking. With that change the script
fetched 128 pages, up from 110.

**Fixed.** The script now fetches only what `llms.txt` lists. It also strips the Mintlify footer the site added to
every page, and trailing blank lines. `make api-docs` fetched 128 pages, and they are identical to the normalized copy
this check was made from.

<a id="issue-3"></a>

#### 3. Docs cache: the notes describe the September API

Missing from or wrong in `jev-docs/jev-api.md` and `sdks.md`:

- Request rules: a 32 MiB body (`413`), UTF-8 without a BOM, the 64-level nesting limit, finite numbers only.
- Compression: `Content-Encoding: gzip`, `x-gzip` or `zstd`, at most one layer, a zstd window of at most 8 MiB, `415`
  otherwise.
- New errors `400`, `413` and `415`, and `400 max_tokens_exceeded` when a request exceeds the context length.
- Jev 1.14 (`jev-1.14.0`, 2026-10-14), with `jev-preview` now pointing at it. §7's table says `jev-preview` →
  `jev-1.13.0`.
- Context limits are now named `per_request_context` and `per_question_context` (64k and 32k), and the
  `TypeSafe-Danger-Zone-Long-Context: true` header raises both to 262k. There is "no limit on the number of
  questions"; the old notes cite a budget of about 32,000 tokens.
- Rate limits are now set per organization, in tokens and requests per second, and listed in the console. The fixed
  "250,000 tokens/s and 1,200 requests/min" row is gone.
- "Text only" (§1, §7) is no longer true: images are accepted experimentally (#4), and there is a fourth question
  type (#5).
- SDKs: Python 0.7.5 (zstd by default, `Image`, `Box`, `attach_assets`, stricter API-key checks: no internal
  whitespace, control characters or non-ASCII) and JS 0.7.0 (Node.js 22 or newer, zstd, `image()`, `box()`,
  `withAssets`, `compression` option, nullable `usage` counts, payload types no longer exported).
- §9 (the legacy preview API) cites the migration guide, which no longer exists. Keep §9's field list, since it is
  now the only record.
- `jev-docs/README.md`: the fetch date, the SDK versions and the page count (110 → 128).

**Fixed.** `jev-api.md` gains sections on the request rules (with the nesting probe's results) and on images and Box.
It also updates the errors table, the models table (Jev 1.14, context limits, long context, per-organization rate
limits), confidence (§6 now gives the documented formulas; the old note that Choice confidence tells a close
runner-up apart was wrong under them), jaggedness item 8 (now Choice option order), the §9 provenance note, and the
§10 client notes. `sdks.md` covers Python 0.7.1–0.7.5 and JS 0.7.0: compression, assets and multipart, Box types,
nullable `usage`, the JS state and Noul rules, the new validation list, and the changelog. `README.md` has the new
date, versions and page count. `cookbooks.md` is split out as #9.

### Low

<a id="issue-4"></a>

#### 4. Gap (experimental): images and the `assets` map

An image can go anywhere text can: a string in `state`, `instructions` or `criteria` holds a reference. Each
reference is a key in a new top-level `assets` map, either `{"type":"image","format":"jpg","data_base64":"…"}` or
`{"type":"image","part":"<name>"}` for a `multipart/form-data` upload, where the JSON is the first part, named
`request`. Every request with an image needs `TypeSafe-Danger-Zone-Images: true`; without it the API returns `400`.
There are limits on format (PNG or JPEG), file size (16 MiB), dimensions (256 to 1568 px), total pixels, and
reference length (1,024 bytes each, 64 KiB in total). TypeSafe calls the feature "Dreamer-ready", meaning not yet
production quality, and says its format can change between releases. Jev 1.13 and 1.14 both accept images.

jev4k has no model for any of this, but base64 assets already go through the escape hatches:
`JevCallOptions.extraBody["assets"]` (`REQUEST_FIELDS` blocks only `state`, `model` and `questions`) plus the header
in `headers`. Multipart can't be sent. I didn't run this path.

<a id="issue-5"></a>

#### 5. Gap (experimental): Box questions

A Box question, ``{"type":"box","instructions":"the coffee mug in `photo`"}``, takes no `criteria`. It returns
`{"type":"box","box":{"top","bottom","left","right"},"confidence"}`, edges as fractions from 0 to 1, needs an image
and Jev 1.14 (`jev-preview` or `jev-1.14.0`), and comes under the same "Dreamer-ready" label. `Question` is sealed to
three subtypes, so jev4k can't send one. A Box answer decodes as `UnknownAnswer(type = "box", raw)`, as designed.
First-class support would need `BoxQuestion`, a `WireQuestion` subtype, `BoxAnswer`, a DSL builder, decoding and an
ABI update. It only makes sense together with #4.

<a id="issue-6"></a>

#### 6. Gap: the long-context header is undocumented

`TypeSafe-Danger-Zone-Long-Context: true` raises both context limits to 262k tokens on Jev 1.13 and 1.14, at the same
price per token but slower and less accurate. It already works as a client header or through
`JevCallOptions.headers`. A sentence and a snippet on the site's call-options page would cover it.

**Fixed.** The site's Making Calls page has a "Long context" section with a new compiled example
(`ClientExamples.kt:long-context`). The State page's context-limits bullet links to it, and the README's per-call
options section has a sentence on it.

<a id="issue-7"></a>

#### 7. Gap: request compression

The API accepts one compression layer: gzip, `x-gzip` or zstd. Python 0.7.5 and JS 0.7.0 compress bodies of 1 KiB or
more with zstd by default. Uncompressed bodies are still valid, so nothing is broken. Adding compression would mean
gzip through Ktor, since Ktor has no zstd encoder on every target. Worth doing only if large states make upload size
matter, so defer it.

### Nit

<a id="issue-8"></a>

#### 8. Docs: "text only" and "three question types"

`docs/packages.md:8` and the site's question pages say "there are three question types", which is true of jev4k but
not of the API. Suggested wording: "jev4k supports Jev's three production question types", plus a line on the
experimental images and Box support. Leave `CHANGELOG.md:234` and `RELEASE_NOTES.md:182` alone, since they record
releases.

**Fixed.** The README, `docs/packages.md` and `llms.txt` now say "jev4k supports three question types" (or kinds of
question). The README adds a paragraph on Box. The README, the Concepts page and the State page say Jev reads text,
that image support is experimental, and that jev4k doesn't send images yet. The Concepts page also lists
`jev-preview` as `jev-1.14.0`. The home page's "Three kinds of question" heading stays, since it describes jev4k.
I used plainer wording than the suggested "production question types".

   `Answers.kt`, `Errors.kt`, `JevCallOptions.kt` and `JevConfig.kt`. No live API calls were made.
